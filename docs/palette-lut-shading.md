# 调色板明暗处理（LutCanvas）

## 为什么不是 multiply

普通做法是 `COLOR.rgb = src * light`。在像素游戏里这会出两个问题：

1. **发灰**：乘一个 <1 的系数会把所有色相一起往黑拉，饱和度不变但明度全掉，画面变浑
2. **压黄/压蓝**：如果光色本身带色偏，乘上去会让整幅画偏色，原本精心配的调色板被破坏

LutLight2D（Unity 插件）的做法是：**给调色板的每个颜色单独定义一条明暗梯度**。
压暗时不是乘系数，而是换成同色族里更暗的那个真实调色板色。色相与饱和度天然保持。

本实现把这套思路搬到 Godot 4 的 `canvas_item` shader。

## 结构

```
_ToolScript/gen_palette_ramp.py     ← 生成 ramp（读 north 39 色，按色族切阶梯）
        ↓
Assets/Shaders/Ramps/north_ramp_7.png   39×7，X=颜色，Y=明度档，中间行=原色
        ↓
Assets/Shaders/Screen/LutCanvas.gdshader
        ↓
全屏 ColorRect（挂在要被处理的画面之上、UI 之下）
```

## 色族是怎么分的

north 39 色本身是按色族排列的（earth 15 / green 5 / brown 5 / gold 5 / red 3 / gray 6）。
生成器不靠硬编码索引，而是按**声明顺序**扫过去，相邻两色满足任一条就判定换族：

- Δ色相角 > 20°
- chroma 比 > 2×

然后逐块验证 **L\* 单调递增**——不单调就说明切错了，直接报错。实测 6 块全部单调。

> 为什么不用聚类：试过 Lab 的 a\*b\* 单链接聚类，暗色的 chroma 天然偏低，
> 会把 `#14140e`（暗土褐）误判进灰族，还会把土褐（chroma≈18）和金色（chroma≈53）
> 合成一族（色相几乎相同）。按声明顺序切块反而最贴合作者意图。

## ramp 怎么用

- **X 轴** = 调色板第 i 色
- **Y 轴** = 明度档，上暗下亮，中间行是原色
- **族内步进**：`target = clamp(pos + (band - center), 0, len(family)-1)`
  → 色族两端自动钳制：最暗的不能再暗，最亮的不能再亮

shader 用 `textureSize()` 读 ramp 尺寸、从**中间行**读调色板，
所以换 ramp 图（换主题、换档数）都不用改 shader。

## shader 参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `ramp_texture` | — | ramp PNG，必须 `filter_nearest` |
| `dark_steps` | 1.0 | 暗部压几档（P1 的「两档」= dark 1 + bright 1）|
| `bright_steps` | 1.0 | 亮部提几档 |
| `dark_lstar` | 38.0 | 低于此 L\* 走满压深 |
| `bright_lstar` | 62.0 | 高于此 L\* 走满提亮 |
| `mix_amount` | 1.0 | 与原图混合量 |
| `max_match_distance` | 0.06 | 越界放过阈值，见下 |
| `debug_mode` | 0 | 1=调色板索引（越界标品红），2=档位 |

有效分档（默认参数下）：**L\* < 44 压深一档，44–56 不动，> 56 提亮一档**。

## 越界放过（max_match_distance）

**这是必要的，不是可选优化。**

调色板内部两两最近邻距离的中位是 **0.088**，而 pixelfx 特效像素到最近 north 色的
距离中位是 **0.10–0.12、P90 到 0.45**——特效颜色落在色板网格的空隙里。
无条件吸附会把特效的青/蓝/紫光晕揉成土色，画面直接变脏。

设成 0.06 之后：

| 输入 | 到最近色板色距离 | 行为 |
|---|---|---|
| 精确的调色板色 | 0 | 正常分档处理 |
| 色块边界的抗锯齿混合 | 0.01–0.03 | 正常处理（仍在阈值内）|
| 特效的紫/青/蓝光晕 | 0.10+ | **原样放过** |
| 任意 RGB（纯红/纯蓝/UI） | 0.4+ | **原样放过** |

设 0 = 关掉限制（回到"总是吸附"的旧行为）。调试时把 `debug_mode` 设 1，
越界像素会显示成品红，一眼看出哪些内容没被调色板覆盖。

⚠️ 实现上有个坑：Godot 的 `fragment()` 里**不能用 `return` 提前退出**，
否则报 `SHADER ERROR: Using 'return' in the 'fragment' processor function is incorrect`，
整个 shader 编译失败、画面变全白。所有分支必须落到一个 `result` 变量再一次性写 `COLOR`。

⚠️ 另一个坑：`ramp_texture` **不能**标 `source_color`。标了之后采样值在线性空间，
而 `screen_texture` 是 sRGB 编码值，直接比较距离会虚高几十倍、全部误判成越界。
要么两边都不转换（当前做法），要么两边都转——不能只转一边。

## 图层顺序（关键）

```
ContentLayer (layer 0)     场景、精灵、图块 ← 会被处理
ShadeLayer   (layer 50)    ColorRect + LutCanvas
UILayer      (layer 100)   文字、HUD、按钮 ← 必须在这之上
```

把 UI 放在 shade 之下会把抗锯齿文字量化成调色板色，边缘发硬、小字更糊。

## 光照驱动（P2）

### 为什么需要

默认的自明度驱动本质是**调色板空间里的对比度曲线**：它看的是像素自身的亮度。
后果是同一块地面无论在灯下还是墙角，处理完全一样——没有体积感。

实测（测试台整屏铺同一个 `#7a6a4c`）：

| 模式 | 亮点 L\* | 中点 L\* | 暗点 L\* | 亮暗差 |
|---|---:|---:|---:|---:|
| 关闭 shader | 45.6 | 45.6 | 45.6 | 0 |
| **自明度驱动** | 45.6 | 45.6 | 45.6 | **0.0** |
| **光照驱动** | 51.9 | 45.6 | 40.6 | **11.3** |

自明度对同色像素给出完全一样的处理（跨度 0.0）——这就是它做不到光照的原因。

### 用法

```glsl
use_light_mask = true
light_mask     = 覆盖整个屏幕的灰度图（0=全黑 1=全亮）
light_contrast = 1.0   # 拉开光暗差别，<1 变平、>1 更强
light_bias     = 0.0   # 整体亮度补偿
```

驱动信号：

```
t = clamp((light - 0.5) * light_contrast + 0.5 + light_bias, 0, 1)
```

`t` 直接接进原有的档位计算（`t < 0.5` 走压深、`> 0.5` 走提亮），
所以**换驱动信号不动分档逻辑**，两条路径共用同一套 ramp。

### 光照贴图怎么来

`_ToolScript/gen_light_mask.py` 程序化生成：

```bash
~/miniconda3/bin/python _ToolScript/gen_light_mask.py \
  --size 960x540 --ambient 0.26 \
  --light 260,320,360,0.95 --light 720,180,240,0.55 \
  --out Assets/Shaders/Lights/test_light.png --quantize 6
```

- `--light x,y,radius,intensity` 可重复，平方衰减
- `--quantize N` 把光照量化成 N 档。像素美术里量化过的光照比平滑渐变自然
  （不会有噪点般的抖动）
- 尺寸必须等于游戏视口：shader 用 `SCREEN_UV` 直接采样，不做坐标变换

### 局限（重要）

光照贴图是**屏幕空间**的，不是世界空间的：

- 相机移动/缩放时贴图要跟着动，否则光影会"粘"在屏幕上
- 现在没有和 `Light2D`/遮挡体联动，暗部不会自动绕开物体
- 精度取决于贴图分辨率，不是逐光照计算

要做真正的动态光影，两条路：
1. 把 `Light2D` 的渲染结果导到一张 `SubViewport`，用它当 `light_mask`
2. 或者放弃屏幕后处理，改成逐精灵的着色器 + 光照纹理

当前实现适合：固定镜头、烘焙式光照、或"昼夜/室内外"这类整体明暗变化。

### 验收

`CaptureLutLighting`（已接入 `runAll.sh`），三条断言：

1. shader 关闭时三个采样点必须同色（否则对照实验不成立）
2. **自明度模式下三点跨度必须 ≈ 0**（证明它是同色同处理）
3. **光照模式下亮点必须比暗点亮 > 8 L\***（证明光照真的在驱动）

反向用例：把光照贴图换成全白，亮暗差变成 0.0，断言报
`光照模式下亮暗差只有 0.0（要求 >8.0），光照贴图没起作用`。

⚠️ 采样点的定位十字要画在采样点**上方**，不能盖在采样点上——
否则读到的是标记色（`#d8c8a8`），整个对照实验失效。这个坑真踩过。

## 已知限制

1. **只处理调色板内的素材**
   它在调色板内做最近色替换；调色板外的颜色按 `max_match_distance` 越界放过、
   保持原样（不再是硬吸附）。所以：
   - 已经过 `palette_unify` 的素材 → 正常处理
   - 特效、任意 RGB、没统一过色板的美术 → 原样保留（不会被揉坏，但也不受明暗处理）

   这带来一个纪律：**想让某块内容参与明暗处理，就先把它的颜色落进调色板**。
   靠 shader 硬拉是不行的（也是有害的）。

2. **自明度驱动 vs 光照驱动**
   两者都在 ramp 的档位上工作，区别只在**驱动信号**：
   - 自明度（默认）：看像素自身亮度，是调色板空间的对比度曲线。
     中间调画面几乎不变（场景区 ±2 档只有 −0.5 L\*）。
   - 光照（`use_light_mask`）：看光照贴图，同色像素在不同光照位置落到不同档位。
     实测亮暗差 11.3 L\*。

   光照模式的限制见上一节「光照贴图是屏幕空间的」。

3. **每像素 39 次纹理采样**
   调色板越大越慢。39 色在 960×540 下无压力；若将来色板涨到 200+ 色，
   应改成预烘焙的 3D LUT 或索引图。

## 验收

`Game/MyGame/Tests/Regression/CaptureLutCanvas.tscn`（已接入 `runAll.sh`），窗口模式运行。

判据：

- 39 色原色条的每个色块，输出**精确等于** ramp 里该色的期望档位 → 39/39
- 被改动的像素分三类：**吸附**（输出是调色板色）、**越界保留**（输出与原色差 ≤ 8/255）、
  **异常**（两者都不是）→ 异常必须是 0
- 色相漂移 ≤ 15°
- 场景区饱和度不许掉超 5%（发灰检测）
- 另外硬门禁：脚本挂载、材质就绪、ramp 绑定、两图非空且互不相同
  （这几条是为了防止"没跑起来却报 PASS"的假绿）

反向用例已验证：把 `int band = clamp(center + ...)` 改成 `center - ...`，
断言立刻报 `SWATCH 8/39` 并逐色列出期望值。
